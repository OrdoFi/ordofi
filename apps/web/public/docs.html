OrdoFi Documentation

The execution layer for Robinhood Chain (Arbitrum Nitro L2, chain ID 4663).

Quickstart

# clone & install npm install # 1. measure MEV on the chain npm run watcher # follows the head, writes data/*.ndjson npm run report # USD-denominated report → data/report.json # 2. run the smart RPC gateway npm run gateway # :8547 # 3. run the order-flow auction npm run auction # :8548 # 4. serve the site npm run web # :3000

Gateway API :8547

A drop-in JSON-RPC endpoint. Point any wallet, bot, or app at it. Standard eth_* methods pass through to the chain; OrdoFi adds protection and extensions. Authenticate with an x-api-key header.

eth_sendRawTransaction protected

The transaction is simulated from the recovered sender first. If it would revert, it is rejected with code -32000 and never reaches the sequencer — so you don't pay gas for a guaranteed failure. Otherwise it forwards normally and returns the tx hash.

ordo_simulate

Simulate a raw signed transaction without sending it. Returns { ok, revertReason?, from, to }.

curl -X POST http://localhost:8547 \ -H 'x-api-key: YOUR_KEY' -H 'content-type: application/json' \ -d '{"jsonrpc":"2.0","id":1,"method":"ordo_simulate","params":["0x02f8..."]}'

ordo_sendBundle

Submit up to 10 transactions to be sequenced back-to-back. Every tx is simulated first; if any would revert, the whole bundle is rejected. Params: { txs: [rawTx, ...] }.

Ordering guarantee: best-effort on a first-come-first-served chain — transactions are fired in the same tick to minimize the gap at the sequencer. Enforced atomicity requires sequencer integration (Phase 3) and is documented as such in the response.

Searcher API :8548

Connect over WebSocket to ws://host:8548/searcher to receive order-flow opportunities and bid on backrun rights.

// on connect you receive: { "type": "welcome", "auctionWindowMs": 200, "swapTopics": {...} } // for each user transaction OrdoFi is holding: { "type": "opportunity", "opportunity": { "id": "…", "hint": { "poolsTouched": […], "selector": "0x…", "value": "0x0" } } } // respond with a sealed bid before the window closes: { "type": "bid", "opportunityId": "…", "searcher": "0xyou", "bidWei": "1000000000000000", "backrunRawTx": "0x02f8…" }

Auctions are sealed-bid, second-price: the highest bidder wins and pays the second-highest price. The winning backrun is dispatched immediately after the user transaction.

Verifiable outcomes signed

A sealed-bid auction asks you to take the operator's word for the losing bids. You don't have to. Every bid is acknowledged the moment it lands, and every closed auction publishes a receipt — both signed by the auctioneer under EIP-712, so a discrepancy between them is evidence rather than a complaint.

// the reply to your bid — keep it, it is your leverage { "type": "bid_ack", "opportunityId": "…", "accepted": true, "ack": { "opportunityId": "0x…", "searcher": "0xyou", "bidWei": "1000000000000000", "receivedAt": 1756…, "signature": "0x…" } } // the receipt for the round, once it closes { "opportunityId": "0x…", "winner": "0x…", "clearingPriceWei": "…", "bids": [ { "searcher": "0x…", "bidWei": "…", "receivedAt": 1756…, "bidSig": "0x…" } ], "closedAt": 1756…, "signature": "0x…" }

Three things are checkable from those two objects alone, with no trust in anything the auctioneer says afterwards:

ClaimHow it is checked
Your bid was not droppedThe acknowledged bid must appear in the receipt, at the acknowledged amount
No bids were inventedEach bid carries the searcher's own settlement signature, which cannot be forged for an address you do not hold
Second price was honouredThe winner must be the highest bidder, and must be charged the second-highest bid
import { auditReceipt } from "@ordofi/core/receipt"; const { receipt } = await fetch(`https://auction.ordofi.network/receipts/${id}`).then(r => r.json()); const finding = await auditReceipt(receipt, ack, 4663, auctioneer, SETTLEMENT_ADDRESS); if (!finding.ok) console.error(finding.reason); // signed proof of what went wrong

Signatures make one receipt unforgeable; they do not stop a receipt being swapped out after you have read it. So the auctioneer batches a Merkle root over every receipt it has ever issued into OrdoReceiptLog on-chain. anchoredCount is the prefix that is already immutable, so the gap between it and count is exactly what an operator could still retract.

Sequencer feed ws /feed

MEV here is a latency race rather than a fee auction, and the sequencer feed is where that race starts: transactions appear on it before they are in a block you can query. OrdoFi holds one upstream connection, decodes the Nitro batch framing, and fans the result out — so a searcher gets raw transactions without writing a feed decoder of their own.

// ws://host:8548/feed { "type": "feed_txs", "sequenceNumber": 51709518, "blockNumber": 51654343, "timestamp": 1756…, "receivedAt": 1756…, "txs": [ { "hash": "0x…", "raw": "0x02f8…" } ] }

receivedAt is stamped when OrdoFi received the message, so you can measure the relay's own added latency rather than take it on faith. Throughput and upstream health are at GET /feed/stats: { upstream, clients, sequencerMessages, txsRelayed, lastSequenceNumber, reconnects }.

What this is not: the feed carries transactions the sequencer has already accepted and ordered. It is a head start on decoding, not a preview of pending order flow — that is what the auction is for.

Submitting order flow POST /submit

Wallets and apps route user transactions through the auction to earn rebates:

curl -X POST http://localhost:8548/submit \ -H 'content-type: application/json' \ -d '{"rawTx":"0x02f8…","originLabel":"v4.fun","rebateAddress":"0xapp…"}'

Response includes the auction result and the rebate ledger entry (user / app / protocol split). Check accrued rebates at GET /stats.

Getting a key /portal

Mint one at the portal, or from a script. Supply a rebateAddress and the key routes your order flow through the auction with rebates credited to that address; omit it and the key is protected passthrough only.

curl -X POST https://app.ordofi.network/api/keys \ -H 'content-type: application/json' \ -d '{"label":"my-wallet","rebateAddress":"0xapp…"}'

The key is returned once and only its hash is kept, so a lost key is reissued rather than recovered. Send it as x-api-key to https://rpc.ordofi.network.

Bonds and claimable rebates for any address are readable without a key, straight from the settlement contract: GET /api/account?address=0x…. The portal shows the same numbers, and claims from your wallet.
